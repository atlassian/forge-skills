# What next — the rest of your Forge journey

Read when closing or when asked where to go next. Keep the handoff proportional to completed
work; never describe skipped or failed checks as successes.

State app path, identity, environment, site and observed result. Include limitations such as
untested actions or fallback-only responses. The app can be kept while its site and installation
remain active.

Recap: the manifest declares the app, modules connect it to Atlassian, and backend functions
implement behavior. Explain edit → validate → deploy, with an install upgrade when required.

Use [Build and launch your Forge app](https://developer.atlassian.com/platform/forge/build-and-launch-your-forge-app/)
as the wider map. Offer the relevant next route:

| Intent | Route |
| --- | --- |
| Another app or extending Guru | `forge-app-builder` |
| Failed deploy/runtime behavior | `forge-debugger` |
| External data ingestion | `forge-connector` |
| Preparing for real users | `forge-app-review`; `forge-security-review` or `forge-cost-optimizer` for those concerns |
| Sharing/publishing | Official distribution guidance, with scoped authorization before release |

For inspiration offer [Forge Inspired](https://github.com/atlassian-labs/forge-inspired).
Verify individual example apps before naming them. Do not clone/deploy another app during
the closing message.

Link the actual site, local app folder and
[Developer Console](https://developer.atlassian.com/console/myapps). Invite a next idea if
appropriate; no required "done" reply or final quiz.
